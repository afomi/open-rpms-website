How a release is built

An electronic health record is the server and the programs people actually open.

This page says how we assemble a current copy of the Resource and Patient Management System from the files the Indian Health Service has published, what the chart, the patient panel, and the front desk need from that copy, and what is still missing.

The counts below are from the October 23, 2026 release. A later release publishes a fresh count with itself. The kinds of gaps stay.

The public files are not a build

We treat IHS as having its own way of assembling a release. That way was not part of what was published. We built one, because a current system cannot be stood up from the public files as they arrive.

The last complete public database is from 2021. Everything since arrives as patches, mixed in with installers for the desktop programs. The drop is three kinds of piece, taken from a working system, with no instructions for putting them back together.

A database copy

The stored data of a live 2021 system. That site's queues, mail, accounts, and machine paths are still in it.

Source code

The programs IHS chose to release. Some packages are absent. Some programs exist only as compiled code, with no source.

Patches since

The updates published after 2021, in the patch format IHS uses. Prerequisites cross packages and dates. Desktop installers sit in the same folders.

The recipe we use is ordinary, and it is written down. Every input file is checksummed before it is opened. A hand-written note says which certified version we are aiming at. That note and the patch set become an exact list. The build installs that list and no other. The old site's leftover state is stripped out as its own step. A release is published when the checks pass, with the checksums beside it.

We install IHS's patches as published. When something in the public files is wrong, we look for a later IHS or VA patch that already fixes it. A change of our own is recorded, and it names the defect it repairs.

The certified line, kept current

IHS stamps a certified electronic record with a version. The package that carries the stamp is called BCER. We keep that line current.

The floor is BCER 5.0, the first ONC-certified RPMS configuration under the 2015 Edition Cures Update. The line we maintain now is BCER 9.0, certified in November 2025, with the public patches through July 2026 applied on top.

A release reproduces those patch levels. Running it does not make a clinic certified. Certification belongs to a deployed system that has been through that process.

The same release, on two databases

Each certified level is built twice, from the same packages and the same patches.

InterSystems IRIS

The database IHS runs. You bring the license. The release is a database file with the patches already applied.

YottaDB

The same release, exported and adjusted so it runs without an InterSystems license. YottaDB itself is open source, under the AGPL. This is the port. It is published as a container image with the build. How to obtain the current image is in that project's readme.

The two differ where the database forces it. The one that matters for reuse is the front desk: BPRM talks to RPMS as a database, and that connection exists only on IRIS. The chart and iCare can talk to either.

The programs that make it an EHR

The thing we publish is the server. The first thing that server has to support is the set of programs staff use, not a database on its own.

Our focus stays on RPMS. The work around the programs is the connection: written down, and backed by an example that signs on and asks the server for something real. A server no chart can sign into is not an electronic health record.

VueCentric, the chart

The Windows desktop where clinicians write notes, review results, and place orders. It talks to either database. Most of its files come from the public patch chain. A small set of commercial libraries does not, and a chart built only from public files does not finish starting. That gap is below.

iCare, the patient panel

The program for looking across a group of patients: panels, reminders, and population work, rather than one chart at a time. It has its own connection, and both databases serve that connection. The server side of iCare, through the patches on the current line, is in the release. The desktop program is a separate IHS download.

BPRM, the front desk

Practice management: registration, scheduling, and billing. It reads RPMS through the IRIS database, not through the chart's connection. On YottaDB that path does not exist. Registration and scheduling there go through the server's own interfaces.

The requests those programs make are written up, with examples that run against a release, in rpms-rpc. That library is the supported way to connect a new program.

What is missing, and what that means

The public release is a partial one. These gaps are in every release built from it. Each one changes what you can reuse.

Requests the server advertises, with no program behind them

On the October 23, 2026 release, 203 of 5,592 registered requests have no program in the build or in the public files. 80 belong to packages whose source was not released, including imaging, dental, and parts of the patient chart. 122 belong to names that were never registered as packages. One names no program at all. A program that calls one gets an error. You can reuse the requests whose code was published. You cannot rebuild the withheld parts from this release.

Programs that exist only as compiled code

The 2021 database carries 222 programs as compiled code only. 200 of those have no source anywhere we can find. They do not run, on either database. Menu items that need them do nothing useful. Scheduling has two examples: inactivating or reactivating a clinic, and ambulatory procedures.

The Windows chart is missing libraries we cannot give you

VueCentric is a few hundred files. The public patch chain covers most of them. IHS also licensed commercial libraries onto its own build machines. Those libraries are not in the public files, and they are not ours to redistribute. A chart assembled only from public files stops at "class not registered."

The files a deployer has to supply are the Telerik UI for WPF assemblies (charting, persistence, and the rest of that control set), ComponentOne's grid (vsflex8l.ocx), and the DevExpress libraries the older Delphi screens load (including dclofficexp70.bpl and the rest of that set). A clinic that already has a licensed IHS chart install has these files. A new project gets them from that kind of install, or from the vendor.

A few IHS components are simply newer than an older public snapshot, including the BMX libraries the .NET programs use. Those are fine to use. They come from a later public drop, and they are easy to miss. One context-sharing file is left out on purpose: turning it on hangs sign-on.

The front desk runs on IRIS

BPRM needs the IRIS database connection. YottaDB does not serve it. You can reuse BPRM against an IRIS release, with your own IRIS license and IHS's BPRM installer. You cannot point BPRM at the YottaDB port. The chart and iCare can use that port, within the other gaps on this page.

Drug and procedure codes that are licensed

The National Drug File and the AMA's procedure codes (CPT) are not in the release. The build loads free stand-ins: RxNorm and NDC for drugs, and HCPCS Level II for procedures. A site with its own license can bring the licensed files. The stand-ins are a way to run. They are a different reference set.

Lookup lists that shipped almost empty

39 of 111 standard lookup tables ship with three entries or fewer. Beneficiary has one row of the 31 IHS publishes. The build fills the published lists. A clinic's own vendors, insurers, and facility names are still that clinic's job. Prompts that read an empty list have nothing to offer until someone files the rows.

Imaging

VistA Imaging is not in the build. Part of its patch media was never released. A release here will not view or store images through that package.

The 2021 copy was somebody's live system

Queues, mail, logon blocks, accounts, and paths from the donor site come along in the database file. The build removes them in one step, before a release is published. What you receive is the packages and the reference data we can lawfully load. It is not that site's operations, and it is not your clinic's setup.

What you can take from this

Reasonable to reuse

  • The server on YottaDB, without an InterSystems license, for the packages whose code was published.
  • The same patch level on IRIS, if you have a license.
  • The chart's public files, plus the commercial libraries from a licensed install or the vendor.
  • iCare against either database.
  • BPRM against IRIS.
  • The domain, the workflow patterns, and the security model on this site.
  • The worked examples of signing on and making a request.

Not in the box

  • A drop-in replacement for a production IHS site.
  • Imaging, and the dental and chart features whose code was never released.
  • A complete VueCentric folder you can hand to a clinic with nothing else.
  • BPRM pointed at YottaDB.
  • The licensed drug file and CPT codes, unless you bring them.
  • A certification you can cite. The release tracks the certified patch levels. It is not itself a certified product.

Where the working record is

The build is maintained in the open at lakeraven/rpms-ops. That repository is the record: the inputs, the patch list, the checks, and the current gap count. This page is the plain-language version. When the two disagree, the repository should be believed, and this page should be corrected.

Someone who wants the recipe, including what a future public release from IHS could include so the rest of us would not have to rebuild it, can read the approach notes.

The short patterns of the work, clinical and administrative, stay on Workflows. The step-by-step journeys, with the screen a person sees, are kept in one companion so they are written once. That companion is being prepared for publication. This site will link to it, and will not grow a second copy.
