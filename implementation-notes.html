Implementation Notes

Practical findings from deploying RPMS on modern infrastructure. These notes document version compatibility constraints, workarounds, and integration details that are not in IHS install guides but matter for anyone standing up a working system.

Derived from implementation work across two projects: a development environment (ehr) and a tribal health deployment (yakama-rpms). Last updated May 2026.

The current picture of how a release is assembled, including the YottaDB port and what the public files leave out, is How a release is built. The notes below are older findings from standing a system up.

InterSystems IRIS Version Compatibility

The central constraint that shapes every other decision

The version mismatch problem

The current Docker development image (rpms-iris:pr-7-civicactions) ships IRIS 2026.1.0.234.1 Community Edition on Ubuntu 24.04. BMW 2025.3 — the latest IHS release (November 2025) — requires IRIS 2022.1.3 per its install guide (§2.3). The IRIS.DAT binary database format is version-specific. Mounting BMW 2025.3 on IRIS 2026.1 produces: <DIRECTORY> */usr/irissys/mgr/bmw/.

IHS release cadence gap

IHS has not released BMW for IRIS 2023.x, 2024.x, or 2026.x. The latest BMW (2025.3) still targets IRIS 2022.1.3. This creates a growing gap between the IHS application stack and the InterSystems runtime it depends on.

Community Edition constraints

IRIS Community Edition enforces hard limits that affect a fully-loaded RPMS instance:

  • · Total database size cap: 8 GB
  • · Per-database file size cap: 1 GB
  • · BMW database alone: ~4.8 GB
  • · RPMS database: ~4.2 GB
  • · Combined total: ~10.6 GB — exceeds the 8 GB CE cap

BMW class compilation requires substantial iristemp scratch space. The 1 GB per-file limit causes <FILEFULL> errors during compilation on Community Edition.

IRIS 2026.1 auto-stats bug

IRIS 2026.1 has a bug in %qarTune where auto-stats collection fails when class names differ from SQL table names — which is the case for many BMW classes. Workaround: set AdaptiveMode=0 in iris.cpf.

Implication: Anyone deploying RPMS with BPRM must choose between running a supported but outdated IRIS version (2022.1.3) or running a current IRIS version with workarounds. Both paths are viable but neither is documented by IHS.

IHS Distribution Model

How software reaches facilities — and where the gaps are

Artifact distribution

IHS distributes RPMS artifacts via FTP, organized into Clinical Applications, Administrative Applications, and Infrastructure. Some downloads are restricted to registered IHS and tribal staff. BMW is distributed only as pre-built IRIS.DAT files for Windows and AIX — no Linux build is provided.

No CACHE.DAT since March 2026

Per WorldVistA (March 2026), IHS stopped releasing CACHE.DAT files because they contain proprietary InterSystems content. This narrows the distribution channel to IRIS.DAT binaries and KIDS builds.

FHIR and API initiatives

IHS is building out the 4DH FHIR API: FHIR R4, US Core 6.1.0, USCDI v3. The Centralized Information System (CIS) provides managed cloud access. These represent an emerging alternative path to RPMS data that does not require MUMPS or BMW.

BMW — FileMan-to-SQL Mapping Layer

~22,000 ObjectScript classes that bridge legacy MUMPS and modern web applications

What BMW is

BMW is a pre-built IRIS database (IRIS.DAT binary) containing ~22,000 generated ObjectScript classes. These classes map FileMan files to SQL-accessible tables, enabling .NET applications like BPRM to query RPMS data via ADO.NET without touching MUMPS directly. BMW is a required dependency for BPRM, BQRE, CCDA, and BUSA.

Distribution constraints

BMW is distributed as platform-specific IRIS.DAT binaries (Windows, AIX only). It cannot be imported as XML or KIDS routines in its shipped form. The BMW generator tool is not publicly available. The binary format is locked to a specific IRIS version — you cannot mount a BMW IRIS.DAT built for one IRIS version on a different version.

Working approach: XML class export

The current working method for deploying BMW on Linux IRIS 2026.1:

  1. Extract bmw_2025.3_win.zip and mount the Windows IRIS.DAT in Docker IRIS 2024.3
  2. Export all 22,023 BMW classes as XML (~375 MB)
  3. Import to the staging IRIS 2026.1 instance without compiling ("d" flag)
  4. Compile after import with $system.OBJ.CompilePackage("BMW")
  5. Disable AdaptiveMode in iris.cpf to work around the IRIS 2026.1 auto-stats bug

Status (May 2026): 22,023 BMW classes successfully exported and imported. BPRM login and ADT workspace are working on Linux IRIS 2026.1.

Alternative: FM2Class wizard

IRIS includes a built-in FM2Class wizard that can regenerate BMW-style table classes from the FileMan data dictionary. This produces ~2,000+ classes from targeted files. Settings: Package=BMW, Table Name Format=<FILENAME>, Compile Classes=checked. Limitation: some computed fields produce runtime errors — an FM2Class limitation, not a FileMan issue.

Key FileMan files mapped by BMW

File #2 → BMW.VA_PATIENT

File #200 → BMW.NEW_PERSON

File #9000001 → BMW.PATIENT

File #9000010 → BMW.VISIT

Plus ~19 additional parent files with subfiles.

BPRM — Practice Management

Browser-based registration, scheduling, and ADT workflows

What BPRM is

BPRM v4.0 Patch 6 (November 2025) is the IHS Practice Management Application Suite. It is an ASP.NET application running on Windows Server with IIS. It provides browser-based access to patient registration, scheduling, and ADT (Admit/Discharge/Transfer) workflows. BPRM connects to IRIS via ADO.NET on port 1972 (SuperServer) in the RPMS namespace.

Technology stack

  • · Application server: Windows Server 2016+ with IIS 10+
  • · Runtime: .NET Framework 4.8+ and .NET Core 8.0.17+
  • · Client: Windows 10+ with Edge or Chrome
  • · Database connection: InterSystems ADO.NET provider on port 1972
  • · Data layer: BMW 2025.3 (FileMan-to-SQL mapping)
  • · Application classes: 122 stored procedures and views in bprm0400.06.xml

IRIS driver incompatibility

The BPRM MSI installer bundles InterSystems.Data.IRISClient.dll version 2022.1 (848,384 bytes). This driver cannot connect to IRIS 2026.1. Workaround: swap it with the 2026.1 version of the driver (788,480 bytes), available from the IRIS container at /usr/irissys/dev/dotnet/bin/net8.0/.

RPMS package prerequisites

BMW 2025.3+

PIMS 5.3 p1019

AG 7.1 p17

XU v8.0 p1018+

DI v22 p1018+

BSDX v3.0

Security finding: hardcoded encryption key

BPRM v4.0 p6 uses AES-128-CBC to encrypt its database connection string. The encryption key and IV are static and hardcoded in BPRM.Util.Encryption.AESService. The same key is used across all BPRM v4.0 p6 installations. Since the key ships inside the publicly downloadable MSI installer, the encryption is effectively no protection. A responsible disclosure was submitted to HHS in May 2026.

VueCentric — EHR Thick Client

The clinical GUI layer for IHS EHR v1.1

What VueCentric is

VueCentric is a proprietary multi-tier component framework authored by Medsphere Systems Corp. It provides the graphical user interface for IHS EHR v1.1. It is a Delphi 7 x86 (32-bit) Windows thick-client application, launched as VIM.exe. It is not openly redistributable.

Protocol: CIA broker, not XWB

VueCentric uses the CIA (Medsphere) broker protocol on port 9200 — not the standard XWB RPC Broker on port 9100. The CIA protocol uses a callback model: IRIS dials back to the Windows client on an ephemeral port. This means bidirectional TCP must be open between server and client. In Docker/VM environments, NAT patches are required to two server-side routines:

  • · XWBTCPL ~line 101: comment out NAT IP selection
  • · CIANBACT ~line 23: prefer CIA("IP") over $$CLIENTIP^CIAUOS

Architecture components

VIM

Visual Interface Manager — composes the UI

CSS

Component Support Services — context, events, remote data access

CMS

Component Management Service — just-in-time deployment, versioning, security

CSL

Communication Service Layer — authentication, host data exchange

Installation and patching

EHR v1.1 base plus 40 patches (p1–p40) are available from IHS. The base installer alone is missing ~30 DLLs; the cumulative patch installer (ehr_0110.39.exe, 62 MB) is required for a functional client. Server-side: 42 KIDS builds must be installed (base + 40 patches). Client-side: OCX and DLL files must be registered with regsvr32.

Known issues

  • · Missing dclofficexp70.bpl (DevExpress OfficeXP Controls for Delphi 7) causes electronic signature service failures
  • · Four components fail to register: BEHESigService.dll, BEHOrders.ocx, BEHReports.ocx, BEHQOWizard.ocx
  • · "User context could not be located" → set CIAVM DEFAULT SOURCE XPAR
  • · "Unable to start patient service" → fix division pointer in NEW PERSON file
  • · "Unable to start CPRS Context Adapter" → add OR CPRS GUI CHART menu to user

Current status (May 2026)

VueCentric clinical desktop is running. Menu bar shows User, Patient, Tools, Help. Remaining non-fatal errors in BEHCONTEXTADAPTER, BEHOPTIONS, and component initialization.

The Dependency Chain

The central challenge is a version-locked dependency chain between three components. Both workarounds identified below are in place and functioning.

Pattern: Version-locked binary artifacts create invisible dependencies that surface only at deployment time. When the release cadence of the database engine (InterSystems IRIS) outpaces the release cadence of the applications built on it (BMW, BPRM), the gap compounds. Any modernization path for RPMS must account for this coupling.
