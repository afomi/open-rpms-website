Install RPMS

Each release of RPMS is built from the public IHS files, checked, and published with its evidence. There are three ways in, depending on where you start. Each path says what you get, what you need, the commands to run, and how you know it worked.

Choose your path

1. YottaDB

You want RPMS running in minutes, with no license. One container image.

2. IRIS, your own license

You run IRIS, need BPRM, or need the engine IHS certifies. Two databases you mount.

3. KIDS, into RPMS you run

Your site already runs RPMS and takes changes as KIDS patches, the usual way.

Building software on RPMS? Take path 1, then the first call from code. Want to see it without installing anything? Try the demo.

What's included, by engine

Both engines carry the same RPMS packages at the same IHS patch level, and the same demo clinic. They differ in what runs around them.

Certification. IRIS is the engine IHS certifies RPMS on. Every release reproduces a certified IHS patch level, and no release is itself a certified deployment. The YottaDB line is not certified today, and we intend to pursue it.

How the two builds run the same FOIA code, and what YottaDB does not have yet: two engines, one FOIA.

Before you start

  • Releases are named like bcer-9.0-20261110-55d9e3e-ydb: the certification line, the build date, the commit, and the engine (-ydb or -iris). New releases come out often. The YottaDB image's latest tag always names the newest release, so the command below runs it without looking anything up. Each release is also tagged with its own name, for when you want to stay on one.
  • Each release's notes are its MANIFEST.md file: what it contains, layer by layer, and what each client expects. Beside it is the evidence: the client calls it answered, each persona's first steps, and a patient registered and read back. The notes, and the releases page that lists them, open with the openrpms repository.
  • The demo data is synthetic. The brokers speak plaintext, so keep their ports on your own machine or a private network, and never load real patient data into a demo instance.

The demo personas

These sign-on pairs are published with every release, on both engines. Each is a member of the demo clinic's staff, with that role's menus and keys. The verify code is the access code followed by !!.

  • PROFILE,MD, a physician: PMD123 / PMD123!!
  • PROFILE,RN, a nurse: PRN123 / PRN123!!
  • PROFILE,MA, a medical assistant: PMA123 / PMA123!!
  • PROFILE,REG, patient registration: PREG123 / PREG123!!
  • PROFILE,REGSUP, a registration supervisor: PRSUP123 / PRSUP123!!
  • PROFILE,SCHED, a scheduler: PSCH123 / PSCH123!!
  • PROFILE,BILL, a billing technician: PBIL123 / PBIL123!!. This persona works in the terminal only, so the brokers refuse it.

Path 1: YottaDB (open source)

What you get
One container image with RPMS, the demo clinic and TaskMan. It serves the CIA broker on 9100, the BMX broker on 9101 and the terminal over SSH.
What you need
A machine with Docker and ssh, and about 20 GB free. The image is built for x86-64. On Apple Silicon it runs under emulation, and Docker warns that the image's platform does not match the host. That warning is expected, and the image works.

One command pulls the newest YottaDB release and runs it. No account or login is needed. Set any password you like for the terminal's SSH account.

The public image is coming soon: it is published once a licensing question is answered, and until then this pull is refused as unauthorized. 

docker run -d --name rpms \
  -p 127.0.0.1:9100:9100 \
  -p 127.0.0.1:9101:9101 \
  -p 127.0.0.1:2222:22 \
  -e RPMS_SSH_PASSWORD='choose-one' \
  ghcr.io/lakeraven/rpms-ydb:latest
docker logs -f rpms                   # wait for "TaskMan live", then Ctrl-C

Every port is published on 127.0.0.1, so only this machine can reach it. Keep it that way: the brokers speak plaintext and are meant for your own machine or a private network. To stay on one release, put its name in place of latest, for example ghcr.io/lakeraven/rpms-ydb:bcer-9.0-20261110-55d9e3e-ydb.

The first run downloads about 6 GB. Once the image is local, it reaches "TaskMan live" in under a minute.

Open the terminal, called roll and scroll. The first time, ssh asks whether to trust the container's host key: answer yes. Give the SSH password you chose, and you land at the RPMS sign-on. The codes you type are not shown. 

ssh -p 2222 rpms@127.0.0.1
ACCESS CODE: PMD123
VERIFY CODE: PMD123!!

Good morning PROFILE,MD
Site set to DEMO IHS CLINIC

Select IHS Core <TEST ACCOUNT> Option:

You know it worked when

  • docker logs shows TaskMan live.
  • The sign-on greets PROFILE,MD and stops at Select IHS Core <TEST ACCOUNT> Option:.

Type ^ at an option prompt to step back, and at the main menu it signs you off. If a persona is asked for a terminal type, press Enter to take the default. The SSH account can do nothing but reach the sign-on: no shell, no file copy, no port forwarding.

Everything you change lives inside the container. docker rm -f rpms removes it, and the next docker run starts again from the release. A new container has a new host key, so before you connect to it, forget the old one with ssh-keygen -R '[127.0.0.1]:2222'.

Path 2: IRIS for Health (bring your own license)

The IRIS path opens when the openrpms repository does. Its databases are release downloads and its standup script lives in that repository, so the commands below work from that day on. Until then, path 1 runs the same RPMS on YottaDB.

What you get
A patched RPMS database, IRIS.DAT, with the IHS patches already installed, plus the BMW database that the BPRM web tier reads. The standup script, bin/standup.sh in the openrpms repository, mounts both in an IRIS for Health container and configures them.
What you need
Your IRIS for Health license key, and the IRIS for Health image it covers, named in IRIS_IMAGE. Images from the InterSystems registry need an InterSystems login to pull. Releases are built on IRIS for Health 2022.1, which the registry no longer serves, and a release also runs on 2026.2. Docker, curl, jq, git and ssh, and about 45 GB free: 20 GB for the engine and 25 GB for the downloaded databases and the copy the standup makes. 
TAG=$(curl -s "https://api.github.com/repos/lakeraven/openrpms/releases?per_page=100" \
  | jq -r '[.[] | select(.tag_name | endswith("-iris"))][0].tag_name')
echo "$TAG"                           # the newest -iris release
URL=https://github.com/lakeraven/openrpms/releases/download/$TAG
for f in IRIS.DAT BMW-IRIS.DAT; do
  curl -LO "$URL/$TAG-$f.gz"
  curl -LO "$URL/$TAG-$f.sha256"
  gunzip -k "$TAG-$f.gz"
done
shasum -a 256 -c "$TAG-IRIS.DAT.sha256" "$TAG-BMW-IRIS.DAT.sha256"

git clone https://github.com/lakeraven/openrpms
IRIS_IMAGE=containers.intersystems.com/intersystems/irishealth:<your version> \
IRIS_KEY=/path/to/iris.key \
RPMS_SSH_PASSWORD='choose-one' \
  openrpms/bin/standup.sh ./$TAG-IRIS.DAT

The script finds the BMW database beside the RPMS one. It names its container rpms-iris, so it does not touch path 1's rpms, and it never replaces a container it did not create. If IRIS_IMAGE is missing or cannot be pulled, it stops and says what to set. It takes about five minutes. 

ssh -p 12222 rpms@127.0.0.1
ACCESS CODE: PMD123
VERIFY CODE: PMD123!!

You know it worked when

  • shasum answers OK for both databases.
  • The script prints BUILD-LEVEL: PASS, once the instance passes its checks, and then RPMS up.
  • The terminal on port 12222 signs on as PROFILE,MD.

Inside the container the CIA broker listens on 9200 and the XWB broker on 9100. The script publishes them only when you also set PUBLISH_BROKERS=1, and then on ports Docker picks: docker port rpms-iris lists them. It also publishes the IRIS SuperServer on 11972 and the management portal on 15273. Every port is on this machine only (127.0.0.1), and the script prints where each one landed. If one is already taken, set SSH_PORT, SUPERSERVER_PORT or PORTAL_PORT to another port on this machine, such as 127.0.0.1:12223, or to 127.0.0.1:0 for any free one. A bare port number, without 127.0.0.1:, opens that port to your network.

To try the IRIS path before you have a license, IRIS for Health Community Edition runs a release's RPMS database without its BMW database. Set IRIS_IMAGE=intersystems/irishealth-community:2026.2 and BMW_NONE=1, and leave out IRIS_KEY. Community Edition limits connections and database size, and its built-in license expires a year after the image was built. It is for evaluation, not for running a clinic.

Path 3: KIDS, into RPMS you already run

A KIDS patch is how RPMS sites take changes, and this path follows that practice. It is for your RPMS system administrator.

What you get
Every YottaDB release carries the next patch of our site-local package, LAKERAVEN (namespace LKR), as <tag>-LKR-1.0-<n>.kids, with an install note beside it. Patch 1 carries every routine fix; each later patch carries what changed since the one before. KIDS adds the package to your PACKAGE file on the first install and records each patch in its history. A release can also carry a stand-alone build, such as LKR BMX LISTENER 1.0, the BMX listener iCare uses.
Which sites it fits
Sites running RPMS on YottaDB. Several of these routines are YottaDB rewrites of stock routines, and on IRIS they would replace working code. A site on IRIS keeps taking IHS's own patches; our IRIS releases carry their fixes inside the database.
What you need
Programmer access to the Kernel Installation & Distribution System menu, a snapshot of your database taken just before (KIDS has no uninstall), and the patches in order, from patch 1.

Download every LKR patch and its install note, then list the patches in the order they install. The patches are release downloads, so this command works once the openrpms repository opens, like path 2. 

curl -s "https://api.github.com/repos/lakeraven/openrpms/releases?per_page=100" \
  | jq -r '.[].assets[] | select(.name | test("-LKR-1\\.0-[0-9]+\\.(kids|md)$")) | .browser_download_url' \
  > lkr-urls.txt
while read -r url; do
  curl -LO "$url"
done < lkr-urls.txt
ls *-LKR-1.0-*.kids | sort -t- -k8 -n

Read the newest install note first. It lists the routines the patch replaces, the patch it requires, and the release that issued each earlier one. Then, for each patch in turn, use the stock KIDS Installation menu:

  1. Load a Distribution: the .kids file.
  2. Verify Checksums in Transport Global.
  3. Compare Transport Global to Current System: a routine whose difference you do not expect is a reason to stop.
  4. Backup a Transport Global: your current copies of the routines, saved in a MailMan message, which is the back-out.
  5. Install Package(s): LKR*1.0*<n>.

Then check the patch from programmer mode: 

W $$PATCH^XPDUTL("LKR*1.0*13")
1

You know it worked when

  • KIDS ends the install with Install Completed.
  • $$PATCH^XPDUTL answers 1 for the patch you installed.

Each patch is packed and checked by its release's gate, which installs it by KIDS into an older release of our image. It has not yet been proven on a YottaDB RPMS other than ours, so we would like to hear how it goes on yours.

Hello world: a first call from code

rpms-rpc is a Ruby client for the RPMS brokers. It needs Ruby 4.0 or later, Bundler, git, and a C compiler for one of its gems. This script signs on to the YottaDB instance from path 1 as PROFILE,MD and prints the first page of the patient list, as a chart's patient picker reads it. Put the two files in a new directory. 

# Gemfile
source "https://rubygems.org"
gem "rpms-rpc", git: "https://github.com/lakeraven/rpms-rpc"
# hello.rb
require "rpms_rpc/cia_client"

client = RpmsRpc::CiaClient.new(host: "127.0.0.1", port: 9100)
client.connect
client.authenticate(ENV.fetch("RPMS_ACCESS_CODE"), ENV.fetch("RPMS_VERIFY_CODE"))

client.call_rpc("ORWPT LIST ALL", "", "1").first(5).each do |line|
  dfn, name = line.split("^")
  puts "#{dfn}  #{name}"
end

client.disconnect
bundle install
RPMS_ACCESS_CODE=PMD123 RPMS_VERIFY_CODE='PMD123!!' bundle exec ruby hello.rb
990051  ALPHA,AVERY
990001  ALPHA,CASEY
990027  ANCHOR,JAMIE
990050  ASHGROVE,SAM
990028  BEACON,DREW

You know it worked when

  • It prints five lines, each a patient's internal number and name from the demo clinic's synthetic patients.

From here, the same client reads and writes through the RPCs RPMS registers. Each release lists them in its rpcs.json. lakeraven-ehr is a web tier built on the same client, and a working example of a larger application.

User interfaces

Staff have traditionally used RPMS through the Windows applications IHS distributes: VueCentric, the RPMS-EHR desktop, and BPRM, the web registration and scheduling. Those interfaces are not included here. A release is the RPMS server, its database and its brokers, and IHS distributes the interfaces to sites. Each release's notes list what each client expects of the server.

You reach a release in three ways:

  • The terminal, over SSH to the sign-on, as paths 1 and 2 show.
  • The brokers, which those clients and other programs such as rpms-rpc connect to, as the hello world shows.
  • The web demo, a running instance you sign in to from a browser.

Where to get help

  • Start with the release's MANIFEST.md, and for a KIDS patch its install note.
  • A release that will not start, sign on or install: openrpms issues. Say which release, which path, the command you ran, and the last lines it printed.
  • The Ruby client: rpms-rpc issues.
  • This page, or anything else on the site: website issues.
  • Your IRIS license or engine: InterSystems.

Please leave out anything about a real patient, and report a security problem privately, through the repository's security page.
